## 1. 이 문서의 위치
DP-0004 본문·`dp4/`는 최종 대결을 **A5(원격·자유배치) vs A8(로컬·pinning)** 로 수렴시켰다. 본 라운드는 팀 디스커션에서 나온 다음을 반영해 그 결선을 **정제**한다:
- A8의 유일 약점(로컬 디스크 유실 → 복구 불리)을 겨냥한 **비동기 복구 체크포인트 tactic(T9)** → 변형 **A8″**. (논의 초기의 "실패 시에만 export(T8)" 안은, T9가 상시 async 백업을 하므로 진단 데이터도 이미 스토리지에 있어 **T9에 흡수**됐다.)
- T9가 A8을 A5에 **한 칸 차이(가용성 ★☆☆→★★☆)** 까지 밀어붙여 결정을 **재개방**한다는 분석(§7).
- Scalability가 "둘 다 ★★★"이 아니라 **어느 유한자원이 먼저 마르느냐로 순위가 갈린다**는 정제(§6.1).

### A5. Serverless / Ephemeral Compute-per-Node (원격·자유배치) — 그대로
- **구조**: 노드 작업 **호출마다** ephemeral 컨테이너(K8s Job/Knative/FaaS)를 띄워 1건 처리 후 종료. 단계 간 20GB 중간 산출물은 **공유 오브젝트 스토리지(claim-check)** 로 write→read 왕복 전달, 컴퓨트는 클러스터 어디든 자유 배치.
- **tactic**: FaaS, Ephemeral, Scale-to-zero, Bulkhead(invocation 격리), Claim-Check, Built-in retry.

### A8″. Co-located Ephemeral Stage + 비동기 복구 체크포인트 (로컬·pinning) — 정제 변형
- **구조(A8 계승)**: 4단계를 **데이터가 있는 노드에 핀(data-affinity)** 으로 박아 실행. 단계는 일회용 컨테이너이나 스케줄러가 **이전 단계가 20GB를 남긴 그 노드**에 배치 → 단계 간 전달은 **노드 로컬 볼륨/스트리밍**. 병목 단계 worker만 비대칭 확장. 노드 용량 초과 시에만 원격 spill(locality-first).
- **추가 tactic(A8″ 신규) — T9 비동기 복구 체크포인트**:
  - **write = 비동기·백업 전용(off-path)**: 단계마다 산출물을 오브젝트 스토리지로 **async 백업**한다. 크리티컬 패스 밖이라 파이프라인은 기다리지 않는다.
  - **read = 로컬만**: 워크플로우 처리(다음 단계 입력)는 **항상 로컬에서** 읽는다. 원격 사본은 처리에 쓰지 않는다 — **오직 노드 사망 복구용**.
  - **복구**: 노드가 죽으면 다른 노드가 **마지막 백업분부터 재개**(통째 재계산 회피). 실패 시 진단 Agent도 이 백업을 읽는다(초기 T8 export 흡수).
  - **footprint 완화**: 백업이 cold 스토리지에 있으니 **retain-until-success 불필요** → 중간 산출물을 **소비 후 로컬 폐기** 가능(A8′의 footprint 압박 해소).
- **핵심 성질**: read가 로컬·write가 off-path라 **Performance ★★★ 유지**하면서, async 백업으로 **Availability ★☆☆ → ★★☆**. 단 async라 **손실 window**(백업 미완 중 노드 사망)가 남아 A5의 ★★★엔 못 미치고, 백업 write가 **공유 스토리지 대역폭을 일부 재점유**한다.

## 4. 캐싱 구분 — 혼동 방지 (디스커션 정리)
"캐싱을 쓰면 되지 않나"는 두 종류를 갈라야 한다:
- **중간산출물 캐싱**: 중간 산출물은 소비자 1명이라 재사용이 0. 캐시가 이득을 내려면 다음 단계를 같은 노드에 앉혀야 하고 → 그건 곧 **data-affinity = A8**. 즉 "A5 + 중간산출물 캐시 + 캐시-aware 스케줄링"은 A8로 **수렴**하므로 별도 안이 아니다.
- **재사용 캐싱**(같은 모델 재빌드·공통 base·증분): A5/A8 축과 **직교**하며 **양쪽 모두에 이롭다**. 캐시 hit는 전달뿐 아니라 **컴퓨트 자체를 skip**하므로 ROI가 더 크다. → 이는 **DP-0005(E2E 캐시)** 영역이며 본 결정에서 분리한다.

## 5. Trade-off 비교 (3 ASR)

### 5.1 택틱 적용에 따른 별점 변화 (baseline → tactic)
각 안은 기준선(1안·2안)에 택틱을 얹어 진화한 것이다. **택틱이 별점을 얼마나 바꿨는지**를 화살표로 표기한다.

| 계보 (직전 → 택틱 적용) | Scal (QA-01) | Avail (QA-02) | Perf-E2E (QA-10) | 적용 택틱 · 효과 |
|---|:---:|:---:|:---:|:---|
| 1안 타입별 상주 풀 (원격 기준선) | ★★☆ ¹ | ★★★ | ★★☆ | — |
| **A5** ← 1안 + 일회용 | ★★☆ **→ ★★★** | ★★★ 유지 | ★★☆ 유지 | Ephemeral·**Scale-to-zero**·자유배치 → 과프로비저닝 0으로 **Scal↑** |
| 2안 co-located 상주 (로컬 기준선) | ★★☆ | ★☆☆ | ★★★ | — |
| A8 ← 2안 + 로컬리티·비대칭 worker | ★★☆ **→ ★★★** | ★☆☆ 유지 | ★★★ 유지 | Data-Locality·**Pipeline Parallelism** → 병목단계만 확장 **Scal↑** |
| **A8″** ← A8 + 비동기 복구 체크포인트 | ★★★ 유지 ² | ★☆☆ **→ ★★☆** | ★★★ **유지** | **T9 async 복구 체크포인트** → 복구 획득으로 **Avail↑**, Perf 보존 |

¹ 원 DP-0004 매트릭스는 coarse하게 1안 Scal ★★★로 뒀으나, 본 정제 라운드는 상주 과프로비저닝·타입별 고정풀을 반영해 ★★☆로 세분한다(→ scale-to-zero가 ★★★로 올림). 원 매트릭스는 그대로 유지.
² T9의 백업 write가 storage 대역폭을 일부 재점유(§6.1 storage-knee 이동) — 단 retain-until-success 불요로 footprint(SP-4)는 오히려 완화. 상쇄되어 별 경계는 불변(★★★), knee 프로파일만 이동.

> **핵심**: T9는 **"성능을 안 깎고(★★★ 유지) 가용성을 한 칸 올리는(★☆☆→★★☆)"** 택틱이다. 비결은 **write는 off-path async·read는 로컬만** — 백업이 처리 경로에 끼어들지 않아 성능을 지키고, 그 백업이 노드 사망 복구를 담당해 가용성을 올린다. 대가는 표 밖 — **공유 스토리지 write 부하 일부 부활**(§6.1 knee 이동)과 **async 손실 window**(§6.2, A5의 ★★★엔 못 미침).

A8 계열의 "스토리지 의존도" 스펙트럼에서 A8″의 위치:

| A8 계열 (스토리지 의존도) | Avail | Perf | Scal(스토리지 부하) | 성격 |
|---|:---:|:---:|:---:|:---|
| A8 base (백업 없음) | ★☆☆ | ★★★ | 없음 | 순수 로컬 — 복구 불가 |
| **A8″ = async 백업 전용 (채택)** | **★★☆** | **★★★** | 일부(write만) | 로컬 read 유지 + 복구 획득 |
| sync eager 체크포인트 (대안) | ★★☆~★★★ | ★★☆ | 더 큼 | 백업이 파이프라인 막음 → **A5로 수렴** |
| A5 (원격 전달) | ★★★ | ★★☆ | 최대(왕복) | 완전 원격 |

→ A8″는 **로컬 read(성능)와 원격 백업(복구)의 의도된 중간점**. 완전한 ★★★ 가용성은 sync 백업(=A5의 write 비용)이라야 하고, 그건 A5로 수렴한다. A8″는 "성능을 지키는 대신 가용성을 ★★★이 아닌 ★★☆에서 멈추는" 선택이다.

### 5.2 A5 vs A8″ 정면 비교

| ASR | A5 — 원격·자유배치 (그대로) | A8″ — 로컬·pinning + async 복구 체크포인트 |
|---|:---|:---|
| **Scalability** QA-01 (ASR#1) | **★★★** — 자유배치 tight bin-packing + backfill + scale-to-zero. 유한자원 knee = **공유 스토리지 대역폭** | **★★★(조건부)** — 병목 단계 worker 확장은 강하나 배치 자유↓. compute 노드/footprint knee + **백업 write가 storage 대역폭 일부 점유**(knee가 A5쪽으로 부분 이동) |
| **Availability** QA-02 (ASR#2) | **★★★** — 오브젝트 스토리지가 산출물 동기 보존 → 노드 사망해도 손실 window 0, 마지막 완료 단계부터 재개 | **★★☆** — async 백업으로 노드 사망 시 마지막 백업분부터 재개(복구 획득). 단 **백업 미완 중 사망하는 손실 window** 때문에 ★★★엔 못 미침 |
| **Performance-E2E** QA-10 (신규 ASR) | **★★☆** — claim-check 20GB 왕복(단계마다 write+read) 전달세금 + cold-start가 E2E 잠식 | **★★★** — 로컬 read + off-path async write로 왕복 회피. 백업이 크리티컬 패스 밖이라 E2E 무영향 |

> 게이트/조건: Scalability는 `rate-limit 헤드룸 ≥20%` 하 scaling efficiency, Availability는 `in-flight 손실=0 AND 멱등=100%` 게이트 통과 전제, Performance는 `throughput ≥50/일 · 전달 무결성=100%` 게이트 하. 별점은 각 QA ★ rubric 앵커의 예시 캘리브레이션 — PoC로 확정.

## 6. 축별 심층

### 6.1 Scalability — 유한자원이 순위를 가른다
무한 자원이면 A5·A8″은 **사실상 동등**(둘 다 일회용·near-linear). 유한 자원에서 갈린다.

**USL (Universal Scalability Law)** — QA-01이 채택한 확장성 정통 모델:

```
   C(N) = N / ( 1 + α(N−1) + βN(N−1) )          scaling efficiency = C(N) / N
```
- **N** = 투입 병렬도(워커·노드 수 또는 부하 배수) · **C(N)** = 1대 대비 상대 처리량
- **α (contention · 경합계수)** = 공유 자원 직렬화·대기 비용(Amdahl 직렬분율). ↑ 하면 처리량이 천장에서 **포화(plateau)**. ⇐ **A5의 지배 항**: 공유 스토리지 대역폭·LLM rate-limit 대기
- **β (coherency · 상호일관성계수)** = 워커 간 조율·동기화 비용. ↑ 하면 knee를 지나 처리량이 오히려 **역행(retrograde)**. ⇐ **A8″의 지배 항**: data-affinity 조율·fragmentation·spill 재조율

> 근거: [WSO2 — Measuring Scalability Using USL](https://wso2.com/blog/research/measuring-software-scalability-using-universal-scalability-law/) · [Perfdynamics — How to Quantify Scalability (N. Gunther, USL)](https://www.perfdynamics.com/Manifesto/USLscalability.html)

`부하 2배 → 1.8배(efficiency 0.9)` 선이 깨지는 N을 **누가 먼저 맞느냐**가 이 축의 비교다:
- **A8″의 확장 단위 = 노드**. 병목 단계 worker 확장은 노드 안에서만 유효 → 파이프라인이 노드 footprint를 넘으면 locality 붕괴·spill. 부하가 오르며 클러스터가 차면 **제약 배치가 먼저 자리를 잃어** knee가 낮은 부하에서 온다(β↑). **단 T9 백업 write가 A5의 절반가량 storage 부하를 얹어**, A8″도 이제 storage-bandwidth 항(α)을 일부 짊어진다(순수 A8은 0이었음).
- **A5의 확장 단위 = 클러스터 전체**. 노드 경계 벽 없음. 대신 20GB 왕복(write+read)이 **공유 스토리지 대역폭**을 선형으로 잡아먹어, 그 파이프가 유한하면 **A5가 거기서 먼저 꺾인다.**

| 먼저 마르는 유한자원 | 먼저 knee가 오는 안 |
|---|---|
| Compute 노드 / 노드 footprint | **A8″** (배치 제약·β↑·노드 천장) |
| 공유 스토리지 대역폭 | **A5** (왕복 write+read) — A8″도 백업 write로 일부 점유하나 read가 로컬이라 A5보다 부하 절반 |
| 공유 LLM rate-limit (계정 전역) | **동률** — 배치 무관, QA-01의 명시 1순위 천장 |
| (양쪽 모두 무한) | **사실상 동등** |

→ Scalability는 "둘 다 ★★★"이 아니라 **어느 자원이 먼저 마르냐로 비교**되며, 이는 노드 사양·스토리지 대역폭·LLM 쿼터의 **실측**이 정한다.

### 6.2 Availability (QA-02) — 복구의 본질은 산출물 무손실
QA-02의 정의가 *"반쯤 진행된 20GB 산출물 유실 방지 + 무손실 멱등 재개"* 이므로, A5/A8 스토리지 차이가 정조준하는 축은 (dp4/의 QA-08 격리가 아니라) **QA-02** 다.
- **A5 (★★★)**: 오브젝트 스토리지가 곧 전달 경로라 **완료 단계가 항상 동기적으로 durable**(손실 window 0). 노드 사망 시 event history + 스토리지로 마지막 완료 단계부터 재개(in-flight 단계만 재실행).
- **A8″ (★★☆)**: T9 async 백업으로 **마지막 백업분부터 재개**(순수 A8의 통째 재계산 회피 → ★☆☆에서 ★★☆로). 단 **async라 "로컬엔 썼지만 원격 백업이 아직 안 끝난 사이 노드 사망"** 하는 **손실 window**가 남아, A5의 손실 window 0(★★★)엔 못 미친다.
- **완전 ★★★ 하려면**: 백업을 **동기(sync)** 로 = 다음 단계 진행 전 원격 write 완료 대기 → **write 전달세금 부활 = A5로 수렴**(Perf ★★★→★★☆). 즉 마지막 한 칸(★★☆→★★★)은 성능과 맞바꿔야 얻는다.

### 6.3 Performance-E2E (QA-10)
- **A5 (★★☆)**: 단계마다 20GB write→read 왕복 = 전달세금. `(4단계×20GB)÷대역폭`이 E2E 5%를 넘으면 latency 잠식(+cold-start).
- **A8″ (★★★)**: 로컬 read + **off-path async write**로 왕복 회피. 백업이 크리티컬 패스 밖이라 E2E latency에 영향 없음 → A8의 성능 우위를 그대로 유지. (백업 트래픽이 노드 I/O·네트워크를 배경에서 조금 쓰나 파이프라인을 막지 않음.)

## 7. T9 택틱의 효과 — A8을 A5에 '한 칸'까지 밀어붙임 (핵심 통찰)
T9(async 복구 체크포인트)를 세 ASR에 걸쳐 보면:
- **Availability(ASR#2)** → **개선 ✓** `★☆☆ → ★★☆` (노드 사망 복구 획득). 순수 A8·초기 A8′(실패-export)가 못 막던 하드웨어 실패를 async 백업이 커버.
- **Performance(신규 ASR)** → **보존 ✓** `★★★ 유지` (read 로컬·write off-path라 E2E 무영향).
- **Scalability(ASR#1)** → **부분 비용 ⚠** (백업 write가 storage 대역폭 일부 점유 → knee 이동. 단 retain-until-success 불요로 footprint는 완화 → 상쇄되어 별 유지).

> 즉 T9는 초기 실패-export(T8)의 "가용성 무효" 한계를 넘어, **A8을 A5에 가용성 한 칸(★★☆ vs ★★★)까지 밀어붙인다.** 남은 그 한 칸은 **async 손실 window** 하나뿐이고, 그걸 없애려면 sync 백업 = A5의 write 비용 = A5로 수렴. **그래서 A8″와 A5의 대결은 이제 "손실 window를 감내하고 성능을 얻을 것인가"라는 단일 교환으로 정제된다.**

## 8. 결정을 가르는 질문 (AND 조건)
1. **[Performance]** `(4단계 × 20GB 왕복) ÷ 스토리지 대역폭` 이 E2E의 **5% budget** 안에 드는가? — 넘으면 A8(로컬) 필요, 들면 A5로 충분.
2. **[Availability]** A8″의 **async 손실 window**(백업 미완 중 노드 사망)와 **노드 preemption 빈도**가 요구(재기동·손실 KPI 게이트) 안에 드는가? — 들면 A8″의 ★★☆로 충족, 안 들면(손실=0 엄격) A5(★★★)만 통과.
3. **[Scalability]** 우리 환경에서 **compute 노드가 먼저 마르나, 공유 스토리지 대역폭이 먼저 마르나?** — 전자면 A5 우위, 후자면 A8″ 우위(백업 부하 감안), 무한이면 동등.

세 질문 모두 **실측 의존**이다. 본 결정은 *구조*를 고정하고 수치는 측정으로 채운다.

## 9. 결정 / 근거
- **수렴 결론**: 후보를 **A5(원격·자유배치) vs A8″(로컬·pinning + async 복구 체크포인트)** 로 압축. 1안·2안은 비교 기준선(각 진화형에 지배).
- **갱신된 별점**: Scal `★★★ / ★★★(조건부)`, **Avail `★★★ / ★★☆`**, **Perf `★★☆ / ★★★`**.
- **우선순위 순 읽기 (재개방됨)**: 초기 A8′(Avail ★☆☆)에서는 가용성이 3칸 대 1칸이라 우선순위상 A5가 사실상 강제됐다. **T9가 그 격차를 한 칸으로 좁혀 결정이 다시 열린다.**
  - **엄격 사전식**이면: Scal 동률 → 다음 우선순위 Avail에서 A5 우세 → **A5**.
  - **그러나 ATAM 실무**(격차 × 우선순위 + 합격선 통과)로는: **A8″의 ★★☆가 가용성 요구를 통과하면** 가용성은 "둘 다 충족"이라 변별력을 잃고 → 결정은 Performance로 내려가 **A8″**. 미통과면 **A5**.
- **택일 기준**: §8의 세 질문. 특히 **Q2(손실 window·preemption 감내)** 가 A8″의 ★★☆를 합격선 위로 올리고 **Q1(전달세금)** 이 A8의 성능 이익을 실이익으로 만들면 → **A8″**. Q2가 손실=0을 엄격히 요구하면 → **A5**.
