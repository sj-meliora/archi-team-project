## 조사한 레퍼런스 — 동일 제품의 두 배포 형태가 보이는 승인 비대칭

Anthropic Claude Code는 **같은 에이전트를 격리 강도가 다른 두 환경**에서 운영하며, 승인 정책이 환경에 따라 달라진다. "정책이 관대해진 것"이 아니라 **격리 경계가 이동하자 승인 경계가 따라간 것** — dp3 TP-1(격리 강도 ↔ 자동존 폭)의 실존 증명이다.

### 1) 로컬 실행 — 격리 없음 → 사람이 곧 샌드박스
- 에이전트가 사용자의 커널·파일시스템·자격증명을 그대로 공유. 격리 경계가 사실상 없음.
- 결과: **Bash 실행 한 건에도 승인 프롬프트** — 높은 승인 빈도는 약한 격리에 대한 보상이다.

### 2) 클라우드 실행 — 일회용 격리 컨테이너 → 경계 통과만 승인
- 세션이 **일회용 격리 컨테이너**에서 구동(fresh clone, 세션 후 회수). egress는 환경 생성 시 선택한 **네트워크 정책·프록시** 경유. 자격증명은 **레포 단위로 스코프**된 세션 토큰.
- 컨테이너 **안**: Bash·파일 조작 전부 자동 승인 — blast radius가 폐기 가능한 컨테이너로 한정되므로.
- 컨테이너 **밖으로 나가는 효과**: PR 생성·push·아티팩트 발행 등 **경계 통과 액션에서만 사람을 부름**.
- 네트워크 egress: 매번 묻지 않되 전면 자동도 아님 — **환경 설정 시점에 사용자가 정책을 1회 선택**하고 런타임엔 집행만.

## 도출 원리 3개

### ① 승인 경계 = 격리 경계
> 액션의 효과가 샌드박스 폐기와 함께 사라지면(가역) 자동 승인, 샌드박스를 넘어 지속되면(비가역·외부 노출) 게이트.

- 위험 티어가 **사람이 유지보수하는 액션 목록**이 아니라 **기계 판정 가능한 구조적 술어**("효과가 컨테이너 폐기 후에도 남는가")가 됨.
- 경계 통과 지점은 인터페이스로 열거 가능(레포 push · 배포 API · credential/secret 접근 · 아티팩트 발행 · allowlist 밖 egress) → C-03 "우회 = 0건" 논증을 액션 단위가 아닌 **인터페이스 단위 봉쇄**로 수행.

### ② 가역성은 격리에서 공짜로 나온다
- 샌드박스 내부 액션의 롤백 = 컨테이너 폐기 → **MTTR ≈ 0**. QA-03 ★ rubric의 "graceful stop + 롤백 ≤30초" 축을 내부 티어는 구조적으로 충족.
- C-03 injection 차단율 `≥70%`가 인정하는 **잔여 ~30% 누수**도, 조종당한 에이전트가 망가뜨릴 수 있는 것이 자기 일회용 컨테이너뿐이면 피해가 경계 게이트 앞에서 멈춤 → 축①(격리 등급)이 축②(자동존 폭)를 정당화하는 논리 사슬.

### ③ 승인 시점의 이동 — 3단 메커니즘
이분법(런타임 매번 vs 안 물음)이 아니라, **사람 결정을 언제 소비하는가**의 3단:

| 메커니즘 | 사람 개입 시점 | 레퍼런스(Claude Code 클라우드) | 본 시스템 대응(예) |
|---|---|---|---|
| 자동 (샌드박스 내부) | 없음 | Bash · 파일 편집 | 파이프라인 노드 실행 · 중간 산출물 |
| **정책 사전승인 (standing)** | **설정 시 1회** | 네트워크 정책 · 레포 스코프 | 내부 레지스트리 배포 · 허용된 외부 API |
| 액션별 HITL | 런타임 매번 | PR 생성 · 아티팩트 발행 | production 배포 승격 · credential · delete |

중간 단(정책 사전승인)이 **축②의 진짜 남은 결정 공간**이다 — 경계 통과 지점 각각을 "정책으로 내릴 것 vs 액션별 HITL로 남길 것"에 배정하는 일.

## 사람 병목에의 함의 (QA-01 정합)

- 이 구조에서 에스컬레이션율은 **액션 수가 아니라 경계 통과 수 ≈ 산출물 수에 비례** — Bash 만 건에 승인 만 건이 아니라, 모델 하나당 배포 승인 한 건. 사람-α항(USL)이 workload 규모에서 분리되는 것이 확장성 핵심.
- 그래도 ≥50모델/일(QA-01 throughput 게이트)이면 배포 경계 전부를 액션별 HITL로 둘 때 **하루 ~50건 승인** → **rubber-stamping(승인 피로 → 형식 승인화) 위험**. 승인이 형식화되면 보안 효과도 사라지므로, "전면 HITL = 안전"은 성립하지 않는다.
- 완화 배정 예: **canary/내부 배포 = 정책 사전승인, production 승격만 액션별 HITL**. C-03의 HITL 100% 게이트는 "고위험 티어"에 걸린 것이므로 이 배정과 모순되지 않음 — 오히려 어떤 통과 지점이 고위험 티어인지 명시하게 강제.

## 한계 (유추 번역 주의)

- 로컬 Claude Code의 승인 프롬프트에는 보안 외에 **사용자 의도 확인**(취향·스코프) 성격이 혼재 — 가져올 것은 "격리가 승인을 대체한다"는 구조 원리이지 승인 빈도 수치가 아님.
- 유추 번역 필요: CC의 "PR 생성" ≈ 본 시스템의 "배포/릴리스", "아티팩트 발행" ≈ "외부 전달". **경계 통과 인터페이스 목록은 본 시스템 기준으로 새로 열거**해야 하며, 그 열거의 완전성이 C-03 "우회 0건" 논증의 상한(red-team 하네스 검증 대상, OI-7 연계).
- 파이프라인 노드 작업(컴파일러 등)은 신뢰도가 높은 코드일 수 있으나, **이슈처리 Agent**는 LLM 판단으로 도구를 고르므로 injection 노출면이 CC와 동형 — 격리 등급 요구는 후자 기준으로 보수적으로 잡는다.
