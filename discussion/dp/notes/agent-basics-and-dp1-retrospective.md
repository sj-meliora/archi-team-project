# Agent란 무엇인가 + 합쳐진 DP1은 왜 실패했나 — 팀 공유 메모

> 작성 2026-06-25 · 대상: 17조 팀원 · 맥락: DP 리뷰 논의에서 정리.
> 용도: (1) Agent 기본 개념 공유, (2) 이전 "합쳐진 DP1"이 리뷰 세션에서 깨진 이유 회고 → DP 재구성·발표 1번 타자 선정의 배경 자료.

## Part 1 — Agent란 무엇인가

### 정의
LLM 에이전트 = **목표를 받아, 도구를 써 가며, 스스로 단계를 밟는 LLM**. 구성요소 5개로 분해하면:

| 구성요소 | 설명 |
|---|---|
| **시스템 프롬프트(지침)** | 역할·규칙·작업 방식 |
| **도구셋(action space)** | 호출 가능한 함수/API — *할 수 있는 행동*의 범위 |
| **모델 티어** | 어떤 모델(성능 vs 비용) |
| **컨텍스트/메모리** | 작업에 적재되는 정보 |
| **eval 하네스** | 출력을 검증·채점하는 장치 |

"특화(specialized)"는 이 중 **어느 축을 좁히느냐**의 문제다. 그래서 "범용이냐 특화냐"는 켜고 끄는 이분법이 아니라 **스펙트럼**이다.

### 범용 vs 특화 — 축별 비교
| 축 | 특화 agent (노드별: IRGen/Quantizer…) | 범용 agent |
|---|---|---|
| 프롬프트 | 노드 전용 지침(Quantizer는 양자화 휴리스틱·에러패턴·CLI 플래그를 안다) | 한 프롬프트가 전 노드 커버 |
| 도구셋 | 좁은 allowlist | 넓은 도구셋, 런타임에 선택 |
| 모델 티어 | 노드별 right-sizing(쉬운 IRGen=저가/어려운 Quantizer=상위) | 한 티어로 통일 |
| 컨텍스트/토큰 | 작고 안정된 prefix → prompt caching 적중↑ | 전 도메인 적재 → 토큰↑·캐시 thrash |
| eval | 노드별 golden set·red-team 가능 | eval이 교차곱을 덮어야 → 귀인 어려움 |
| 결정성 | 노드별 few-shot·낮은 temp → 변동↓ | 일반화 부담 → 변동↑ |

### 장단점
**특화 강점**: ① 노드별 검증·red-team 가능(정확성·일관성) ② 좁은 도구 = 보안 표면 축소 ③ 안정 prefix = 토큰 경제 ④ **프롬프트-레벨 bulkhead**(Quantizer 프롬프트 수정이 IRGen에 무영향 — 범용은 한 줄 수정이 전 노드 상관 장애) ⑤ 독립 버저닝·A/B.
**특화 단점**: 증식/유지비(N개 프롬프트·eval셋)·교차 일관성 동기화·신규 노드 cold-start·라우팅 필요.
**범용 강점**: 유연성(새 노드=도구만 추가)·산출물 적음·교차 전이·라우팅 단순.
**범용 단점**: 도구/컨텍스트 혼동·토큰 낭비·eval 귀인난·모델 right-size 불가.

### 꼭 구분할 두 쌍의 개념 (여기서 혼동이 자주 난다)
1. **라우팅 ≠ 오케스트레이션**
   - 라우팅(dispatch) = "이 산출물을 어느 agent에 보낼까". **고정 파이프라인이면 배선(DAG) 자체가 답** — 똑똑한 판단 불요.
   - 오케스트레이션 = 동적 감독·계획(실패 시 재계획·조건 분기·HITL).
   - → **특화 워커는 라우팅을 필요로 하지 오케를 강제하지 않는다.**
2. **오케스트레이터 *에이전트* ≠ 워크플로 *엔진***
   - 워크플로 엔진 = 순서·재시도·복구·상태의 런타임(durable execution).
   - 오케 에이전트 = LLM 감독자.
   - → 고정 파이프라인의 흐름 제어·재시도는 **엔진** 몫이지 LLM 감독자 몫이 아니다.

## Part 2 — 합쳐진 DP1은 왜 실패했나

### 무슨 일이 있었나
이전 DP1은 **두 결정**을 하나로 합쳤다:
- **축 A**: 오케스트레이터 **有無**
- **축 B**: worker agent **특화 vs 범용**

이를 2×2가 아니라 **평면 3안 리스트**로 제시했다:
- 1안 = 오케 + 특화 · 2안 = 오케 + 범용 · 3안 = 무오케 + 특화 · *(4안 = 무오케 + 범용, 미비교)*

리뷰 세션에서 다른 팀의 반응:
- *"3안에 오케스트레이터 추가하면 1안 아니냐?"*
- *"오케스트레이터 있는 게 좋으면 다 써야지?"*

이 두 마디가 정확히 두 결함을 찔렀다.

### 문제 1 — 직교 2축을 평면 리스트로 납작하게 (격자 은닉)
실제 구조는 2×2였다:

| | **특화** | **범용** |
|---|---|---|
| **오케 有** | 1안 | 2안 |
| **오케 無** | 3안 | (4안) |

1안과 3안은 **축 B는 같고 축 A만 다른 인접 셀**이다. "3안+오케=1안"은 청중이 **격자를 정확히 복원**한 것 — 지적이 옳다. 평면 리스트가 격자를 가린 게 문제다.

### 문제 2 — 교환점 미노출 → 오케가 "공짜 선"으로 보임
"다 쓰지"가 나온 이유 = **오케의 단점이 비교에 안 보였다.** 오케스트레이터는 공짜가 아니라 **교환점(Tradeoff Point)**:
- 있으면 → 제어성↑(중앙 정책·HITL) **/ 가용성↓(SPOF) / 성능↓(hop 병목)**
- 없으면 → 정반대

진짜 교환점이면 "다 쓰지"의 답은 **"아니다, 가용성·성능을 깎는다"**. 그 한마디를 못 하면 청중은 그 축을 "당연히 켜는 스위치"로 납작하게 만든다.

### 중요한 정정 — 특화가 오케를 강제하지 않는다
"특화 워커면 오케가 필요하다"는 흔한 오해다. 필요한 건 **라우팅**이고, 고정 파이프라인(IRGen→Optimizer→Quantizer→Compiler)에선 **엔진/choreography가 라우팅을 해결**한다. 그래서 위 2×2의 **네 칸이 다 성립** = 두 축은 (실현가능성 면에서) **직교**다. 한 축을 고르면 다른 축이 강제되지 않는다.

### 진짜 상호작용은 feasibility가 아니라 *value(한계가치)*
축은 직교하지만, **오케의 한계가치는 워커 특화도·흐름 동적성에 의존**한다. 특화 워커 + 정적 파이프라인이면 오케가 할 *라우팅* 일을 특화+엔진이 이미 가져가 → **오케 한계가치↓**. 오케는 **동적 제어(재계획·HITL·정책)가 binding일 때만** 값을 한다. ← 이게 "오케 좋으면 다 쓰지"에 대한 정답.

### (보너스) 자율 회귀 루프는 오케 필연이 아니다
"Quantizer 결과 이상 → Optimizer로 회귀" 같은 자율성은 기능 요구(FR)지만, **오케 없이 구현 가능**하다:
- **bounded 회귀**(고정 회복 엣지): 워크플로 엔진의 **순환 그래프** + 게이트(결정적 메트릭 or stateless judge) → 오케 없음.
- **open-ended 적응 계획**(회복 행동을 추론으로 *생성*): 이때만 상주 오케가 정당화.
- 우리 회귀는 전자라 엔진+judge로 충분. **"필연처럼 보였는데 아니다"를 증명하는 게 ATAM 최고의 한 방**이다.
- 참고: 설령 오케스트레이션이 FR로 강제돼도, 결정은 죽지 않고 **"有無"에서 "어디 두나(중앙 오케 vs choreography vs 엔진 그래프)"** 로 *이동*한다 — 교환점(중앙 추론 유연성↔SPOF)은 그대로 살아 있다.

### 교훈 (처방)
1. **직교 축은 2×2 격자로**, 평면 택1 리스트 금지.
2. **각 축의 트레이드오프를 따로 노출** — 오케 축: 제어↔가용 / 특화 축: 정확성·토큰·일관성.
3. **각 축의 드라이버 질문**을 명시 — 오케 축: "동적 제어가 binding인가?" / 특화 축: "노드 편차·eval 분리·도구 표면이 binding인가?"
4. **dominated 셀은 명시적으로 격하**(왜 빼는지 한 줄).
5. 우리 **`context/dp/dp4/decision-axes.md`** 가 이미 이 패턴(축 A를 2×2로 재정렬, 1·2안을 기준선으로 격하)을 보여준다 — 같은 방식으로.

### 한 줄 결론
> **"합치고 평면 리스트로 납작하게"가 최악의 조합**이었다. 합칠 거면 2×2로, 나눌 거면 *드라이버가 다른 두 결정*으로. 어느 쪽이든 **각 축의 교환점을 보여야** "다 쓰지"가 다시는 안 나온다.
